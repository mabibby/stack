# /stack:db-change — schema change, the safe way

Rules from `architecture.md` §5.1 / §7 apply. To the user this is "changing what the app stores"
(`${CLAUDE_PLUGIN_ROOT}/references/voice.md`) — never say migration, schema or column to them. The short version:

- Schema is code: `src/lib/db/schema/<feature>.ts`, exported from `schema/index.ts`.
- Migrations are generated, reviewed, committed, applied — in that order. **Never** `db:push`, never
  hand-edit `drizzle/*.sql`, never modify a migration that has been committed (write a new one).
- Auth tables (`schema/auth.ts`) are generated by better-auth: change auth config → regenerate with
  `bun run auth:schema` (wraps `bunx auth@latest generate`; needs `JITI_CACHE=false`, already set in the script).

## Steps

1. **Design in words first** if the ask is fuzzy: what entity, which fields, who owns it, what it links to.
   Prefer a column to a JSON blob; prefer a new table to a nullable field that only some rows use.
2. **Edit the schema.** New table: `id()`, `publicId()`, FK to `user` (or owner) with `onDelete`, fields
   with `.notNull()` where the product guarantees a value, `...timestamps()`, an index on every FK.
   New column on an existing table with data: give it a `.default(...)` or make it nullable, or the
   migration fails on existing rows.
3. **Generate.** `bun run db:generate --name <snake_case_what_changed>` (e.g. `add_project_status`).
   Renames: drizzle-kit asks — choose **rename**, not create+drop, or data is lost.
4. **Review the SQL** in `drizzle/<n>_<name>.sql`. Say out loud what it does. Red flags: `DROP TABLE`,
   `DROP COLUMN`, `NOT NULL` without default on a populated table — confirm with the user before applying.
5. **Apply locally.** `bun run db:migrate` then `bun run typecheck` (types flow from the schema).
6. **Update the code** that reads/writes the changed shape (domain → actions → UI). `bun run check`.
7. **Commit** the schema + migration + code together (via `/stack:ship`). Production applies it on the
   next deploy (`railway.toml` runs `db:migrate` before `start`).

## Recovery

- Generated a wrong migration that's **not committed yet** → delete that `.sql` file and its entry in
  `drizzle/meta/_journal.json` + the matching `drizzle/meta/<n>_snapshot.json`, fix schema, regenerate.
- Local DB in a tangle (early dev only) → `bun run db:reset` (wipes local data, re-runs setup).
- Migration already applied locally but wrong and not yet committed → `db:reset` is the honest option.
- Anything already pushed → write a corrective migration; do not rewrite history.
